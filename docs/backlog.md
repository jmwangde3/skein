# 待办与暂缓的需求

只记「想过、评估过、暂时不做」的东西，免得下次重新讨论。每条写清：解决什么、大概怎么做、为什么先不做、什么条件下再做。

## `--adopt-routes`：把已有子路由收编进工作区

**解决什么**

工作区里已经有好几个各自建过库的子项目，每个子目录都有一份 `AGENTS.local.md`。技能从当前目录向上找，第一个命中的是子目录那份，永远进不了父级的新库。

**大概怎么做**

建库脚本加一个开关 `--adopt-routes`，带上它时：

1. 把扫到的子路由备份到 `<数据家>/<工作区名>/backups/legacy-routes/<相对路径>`
2. 全部备份成功之后，才删除原子路由
3. 删掉的子目录从此继承父级路由

**只搬路由文件，不动 `store` / `checkpoints` / `kb`。** 旧任务不会自动出现在新库里；想找旧任务，按备份文件里记的路径去翻。所以这是「切换」，不是「合并」。

**为什么先不做**

- 目前没有这种工作区，现有部署都是单路由
- 这是会让人误以为「旧任务丢了」的操作，必须在用户明确知情时执行
- 默认拒绝已经挡住了误伤，缺的只是「一次收编多个」的便利

**什么条件下再做**

真出现「三个以上已建库的子项目要并进一个工作区」，或者有人手工删路由删错了。

**现在的行为**

扫到子路由就停下、列清单，交给用户决定（保留独立 / 手工处理 / 以后用这个开关）。

## 批量预建档的额外判据

**解决什么**

只在「用户没指定目标仓、又确实要给全工作区预建档」时才有意义：`git stash` 里躺着没提交的工作、或者改动在 linked worktree 里而主工作树是干净的，这两类仓会被现有三条判据漏掉。

**大概怎么做**

```bash
git -C "$R" stash list -n 1                       # 非空 → 先建
git -C "$R" worktree list --porcelain             # 逐个看 status --porcelain
git -C "$R" branch --no-merged HEAD               # 有未合入分支 → 先建
```

**为什么先不做**

- 目标仓优先后，正常流程只建一个仓，根本走不到批量分支
- 三条额外判据每个多 1–2 次 Git 调用，收益只在高仓数场景出现

**什么条件下再做**

真出现「一次要预建档 5 个以上仓」，且发现漏判影响接手。

## 跨仓依赖自动提升

**解决什么**

用户指定了 `A` 仓，但 `A` 依赖同工作区的 `B` 仓（proto、shared、部署脚本），接手后立刻要用 `B` 的档案，而 `B` 还是 `TODO`。

**大概怎么做**

在被选中仓的 `package.json` / `go.mod` / `pyproject.toml` / `docker-compose.yml` 里搜其他仓名，命中就把对方也标成待建档。

**为什么先不做**

文本匹配会误命中同名变量，而且「依赖」不等于「这次要改」。真需要时，接手方看到 `TODO` 会现场建，只多花几分钟。

**什么条件下再做**

同一工作区里出现「每接一个仓都要连带建两三个档案」的重复劳动。

## 目录深度超过两层的仓

**解决什么**

`monorepo/packages/foo` 这类第三层仓不进索引，也不建档案。

**为什么先不做**

层数越深，扫描成本和误判越多；真有这种仓，把工作区根指到 `packages/` 那层更干净。

**什么条件下再做**

同一个 monorepo 里要分别接手三个以上子包，且不方便改工作区根。
