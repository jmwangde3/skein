# 项目档案：契约

`kb/facts/projects/<仓名>.md`，**每个 git 仓一份**。给第一次进这个仓的 agent 看。

不是 README 的副本，也不是源码摘要。它只回答四个问题：这是什么、从哪进、怎么跑、细节在哪。

## 上限

- **硬上限：4 KB / 70 行**，超过就是失败，不截断——重写或拆到 `facts/` 其他文件
- **正常目标：1–2 KB / 30–45 行**。写满上限说明写多了

## 三态

| 状态 | 含义 | 谁来判 |
|---|---|---|
| `TODO` | 索引里有，档案还没建 | `init.sh` 建索引时全标这个 |
| `PARTIAL` | 建了，但关键字段没核实 | 建档 agent 按分档规则判 |
| `READY` | 入口、运行命令、文档指针都有来源，缺口已列明 | 建档 agent 核对后改 |

**`READY` 不等于「命令已验证」。** 从 `package.json` 读到 `npm test` 只说明声明存在，不等于跑通了。字段里必须区分「声明」和「实测」，否则下一个人会把声明当结论。

## 建档分档：先判要不要读代码

逐仓判断，**任一满足即完整建档**（目标 `READY`）：

```bash
R="<仓路径>"

# 1) 当前任务涉及该仓 —— 由调用方传入，脚本判不了
# 2) 工作树有未提交改动
[ -n "$(git -C "$R" status --porcelain=v1 2>/dev/null)" ] && echo FULL

# 3) 任一本地分支在最近 90 天有提交
latest="$(git -C "$R" for-each-ref --sort=-committerdate --count=1 \
  --format='%(committerdate:unix)' refs/heads 2>/dev/null)"
[ -n "$latest" ] && [ "$latest" -ge "$(( $(date +%s) - 90*86400 ))" ] && echo FULL
```

全部不满足 → **简化建档**：只写头部、定位（若 README 有）、文档指针，状态 `PARTIAL`，不读代码。

Git 检查失败、没有有效 HEAD → 保持 `TODO`，把原因写进索引的备注列。

**为什么不用「最后提交超过 90 天」单判据**：实测一个 33 条目、8 个 git 仓的工作区，8 个仓的最后提交全在 4 天内，90 天阈值一个都筛不掉。而「有没有未提交改动」「有没有活跃分支」能在不读代码的前提下区分「停更但有新工作」和「真的没在动」。

## 模板

```markdown
# <仓名>

- 状态：READY | PARTIAL
- 仓库：<相对工作区根的路径>
- 基线：<完整 HEAD SHA> · <分支> · 工作树 clean|dirty
- 建档：<YYYY-MM-DD HH:MM>

## 定位

<一句话：这个仓解决什么问题、面向什么> — 依据：<README.md / 用户确认 / 推断>

## 入口

- `<相对路径>` — <作用> — 依据：<源码 / 文档 / 推断>

（最多 3 条）

## 运行验证

- `<命令>` — <声明来源>，未实测
- 未发现构建或测试入口

（最多 2 条）

## 文档指针

- `README.md` — <一句摘要>；<什么时候该读>
- `AGENTS.md` — 项目约束；**改代码前必读**

（最多 3 条）

## 缺口

- <缺什么、会影响哪类操作>

（仅 `PARTIAL` 时写。`READY` 但有未核实项也可以写）
```

## 字段来源

| 字段 | 来源 | 可以写不确定吗 |
|---|---|---|
| 仓库、基线、工作树 | `git` 与文件系统 | 不能。拿不到就保持 `TODO` |
| 定位 | README、文档、用户确认 | 可以。写「未核实」，不许编 |
| 入口 | 目录结构 + 有限阅读 | 路径可确认，作用允许「推断」 |
| 运行命令 | `package.json` / `Makefile` / 文档 | 可以。写「未发现」，不许猜 |
| 文档指针 | 实际存在的文件 | 不能。指针必须指向真实文件 |
| 缺口 | 建档时发现的空白 | 鼓励写 |

**三类来源要分清**，写的时候用一个词标出来：

- `[源码]` — 直接读到的
- `[文档]` — 文档里写的，未验证
- `[推断]` — 从命名或结构猜的，可能错

不标来源的句子，下一任会当事实用。

## 黑名单

不许进档案：

- 源码片段、整份配置文件、完整目录树（`find` / `tree` 全量输出）
- `git diff` 全文、完整日志、完整错误堆栈
- 历史流水账、已完成的小步修改
- API key、密码、token、客户数据
- 当前任务归属、租约、检查点内容（那是 `task-checkpoint` 的事）
- 未经核实的架构评价

## 写入与中断恢复

顺序不许换：

```
1. 写 <仓名>.md.tmp
2. 校验：必填字段齐、≤ 4 KB / 70 行
3. 原子重命名到 <仓名>.md
4. 更新 facts/projects/INDEX.md 的状态列
5. git -C <kb> commit
```

中断后恢复：**先看实际文件，再看索引**。

- 索引写 `READY` 但文件不存在 / 字段不全 → 降回 `TODO`
- 索引写 `TODO` 但文件完整 → 核对后改成真实状态
- 有 `.tmp` 残留 → 删掉重写，不要续写

## 命名

- 普通仓：`<仓目录名>.md`
- 同名仓：`<仓目录名>-<路径 hash 前 8 位>.md`，hash 输入是**工作区相对路径**，不是 HEAD
- 索引里永远记相对路径，不靠文件名定位

## 刷新

**按需增量，不设定时任务。**

```bash
# 档案引用的文件有没有变（把路径换成该档案实际记录的）
BASE="<档案里的完整 SHA>"
git -C "$R" diff --name-only "$BASE" HEAD -- README.md package.json AGENTS.md
git -C "$R" status --porcelain=v1 -- README.md package.json AGENTS.md
```

任一非空 → 刷新受影响字段。命令报错或基线对象不存在 → 不能判定为「没变」，标「待核实」。

**HEAD 变了但引用文件没变，不需要刷新**——改的是别处。

## 冲突

档案与现场冲突时，**以 Git 现场和实际文件为准**。档案只是导航。

冲突处理顺序：

1. 按真实代码/配置执行，不要为了迁就档案走错路径
2. 把冲突字段改成实际值，或标「待核实」
3. 改完顺手 `git commit`，让下一个人看到的是修过的版本

**不许**用档案否认当前文件的变化，也不许因为源码变了就宣布旧决策失效——那是两回事。
