# 设计说明：Skein 为什么长成这样

这份文档写给想改它的人。只想用的话，看 [README](../README.md) 就够。

---

## 1. 要解决的问题，本质是信息传递

AI 助手干活有两种断法：

- **软断**：窗口还在，但上下文快满了，细节开始模糊
- **硬断**：窗口关了、换机器了、换了一个助手

两种断法的后果一样：接手的人不知道"做到哪、下一步、什么别再试"。于是重新读一遍全部材料，或者更糟——重复劳动，还把已经验证过的东西又推翻一次。

这不是文风问题，是一道算术题：**读全部材料的成本，随项目变大线性上涨；而真正决定能不能接上的信息，通常不到两页。**

所以目标不是"把文档写薄"，是**把存储和阅读分开**：总量可以涨，每次必读的那一小块保持不变。

## 2. 四条不变量

四个技能各守一条。改实现可以，改这四条就不是 Skein 了。

| 技能 | 不变量 | 为什么 |
|---|---|---|
| `task-checkpoint` | 检查点是**快照**，一任务一份，每次整份覆盖，带 `checkpoint_rev` | 快照能一眼看懂；追加式日记要读到底才知道现状。rev 是自检不是锁——拦得住守规矩的写者，拦不住直接覆盖的人 |
| `agent-handoff` | 接手由 B 发起，A 不必交棒；但同一工作树必须先确认旧写者已停 | 任务归属不等于文件锁：Beads 能改派任务，停不掉 A 已经发出的命令。所以"随时能接手"成立，"随时能安全覆盖"不成立 |
| `project-memory` | 检索六级、命中就停；全库单写者 | 整份加载是最贵的读法；两个写者改同一文件不同行，Git 自动合并且不报错，语义覆盖会静默发生 |
| `agent-collab` | 一任务一工作目录一分支一任务号，并行结束即卸载 | worktree 隔离得了代码，隔离不了知识库——KB 是另一个仓，这是最容易漏的一条 |

## 3. 为什么是 4 个，不是 1 个，也不是 5 个

**1 个（大而全）**：所有规则挤在一个技能里，每次开工都要全读一遍。低频场景（并行）的规则天天占着上下文，这就是在给不常用的功能付租金。

**5 个以上**：拆分越细，技能之间的边界越模糊。比如把"写检查点"和"读检查点"拆成两个技能，就会产生"该先调哪个"的判断成本，而这个判断每次都要做。

**4 个的分界线是"什么情况下会同时用到"**：

- 日常长任务：只需要 `task-checkpoint`
- 换人：`task-checkpoint` + `agent-handoff`
- 沉淀：`project-memory`
- 并行：三个都用 + `agent-collab`

也就是说，**日常只有 `task-checkpoint` 一格是常驻（全局），`agent-handoff` 和 `project-memory` 按项目挂载，第四个只在并行期临时挂。** 常驻的只有一格，这是"省 token"那条需求落在结构上的样子。这条线划在"并行"上，因为并行是唯一会让写入冲突真实发生的场景。

## 4. 关键机制，以及它们防的是什么

### 4.1 租约 300 秒

任务被认领后有 300 秒租约，超时别人可以回收。

- 防的是：进程崩了，任务永远锁死
- 代价是：长任务必须每 4 分钟心跳一次
- 为什么不设更长：崩溃后的等待时间等于租约长度。300 秒是"能忍受的等待"和"心跳不要太频繁"的折中

`reclaim` 有一个坑：它回收**所有**过期租约，不只你手上那个。执行完必须再 `show` 一次确认真实归属。

用户要求换人时，B 可以用 `--force -a` 改派有效认领，不必等 A 释放。但改派**不会终止 A 已经发出的命令**：租约状态不是进程活性检测，3 秒内也分不清 A 是在写、卡住还是已经崩了。所以规矩是——**用户授权 + 确认旧写者已停，才能在同一棵树里落笔**。这不是系统级互斥，是人工确认加 agent 遵守规程；要两人同时干，用 `agent-collab` 隔开工作树。

### 4.2 `checkpoint_rev`

写之前先读 rev，写完 rev+1，写完回读确认。

- 防的是：两个人先后写同一份检查点，后写的把先写的覆盖掉而无人察觉
- 不防的是：直接覆盖文件的写者，以及「栅栏通过」到「文件替换」之间那个窗口——它不是原子操作。所以它叫"自检"，不叫"锁"

### 4.3 知识库单写者 + `proposals/`

Git 只报"同一段冲突"。两个人改不同文件不会冲突；改同一文件的不同行，自动合并、不报错——**语义覆盖就这样静默发生了，事后查不出来。**

所以规则不是"小心一点"，而是"同一时刻只有一个写者，其他人写提案"。

### 4.4 检索六级

索引 → 文件名 → 关键词 → 换词（QMD）→ 回读片段 → 语义。

前三级零成本，第四条开始要建索引。**QMD 的门槛是 50 篇或 1 MB**，低于这个数开了是净负担：建索引、占磁盘、每次调用还要带两个环境变量。

### 4.5 工作区：一个目录，多个仓

库的单位不是 git 仓，是**工作区**——一个目录，里面可以有好几个仓。

定位规则只有一条：**从当前目录向上，找第一个含 `AGENTS.local.md` 的目录。** 不看 git，不看标记文件。

为什么不用 `git rev-parse --show-toplevel`：那会把「一个仓 = 一个作用域」写死。父子目录、多个仓共用一套库、仓外的笔记目录，全都不成立。而向上找 `AGENTS.local.md` 这三个场景都自然成立，还顺带解决了子目录执行的问题。

代价是子目录里不能再放第二份 `AGENTS.local.md`——它会遮住工作区那份。这一条写进了建库流程的第 0 步：先扫一遍，有就让用户决定。

**代码仓操作和库操作是两件事。** `git status` / `worktree` 作用在"当前所在的仓"（`git -C "$PWD" rev-parse --show-toplevel`），知识库操作作用在 `kb` 键指向的独立仓。工作区根本身经常不是任何仓。

所以检查点里记 `repo`：这次任务落在哪个仓。一个工作区好几个仓时，接手方靠它决定去哪儿核对；`worktree` 为空不等于现场没有仓。

**库有主人。** 数据目录里的 `.skein-scope` 写着它属于哪个工作区。`D:/a/项目` 和 `E:/b/项目` 都叫「项目」，默认会落到同一个 `<数据家>/项目/`；这个标记就是拦这件事的：归属对不上就报 `[HANDOFF_GAP]`，让用户换 `--data`，而不是两个工作区悄悄共用一份库。

### 4.6 `AGENTS.local.md` 与 `[HANDOFF_GAP]`

所有机器相关路径集中在**工作区根**的一个文件里，用五个键表达。技能正文只写变量，不写绝对路径。

读不到文件或缺键时，**必须停下报 `[HANDOFF_GAP]`**。这条看起来笨，但它防的是最危险的一类错误：AI 猜了一个"看起来对"的路径，然后在错误的地方读写，而且不报错。

工作区根本身是 git 仓时，这个文件要写进 `.gitignore`。放在 `.gitignore` 而不是 `.git/info/exclude`，是因为 exclude 不随克隆走：换机器、重新 clone 后忽略规则就消失，一份复制过来的 `AGENTS.local.md` 可能被 `git add -A` 带进提交。`.gitignore` 里只有文件名，不含路径或凭证；私有的是内容，而内容永不提交。

### 4.7 建库只归一个技能，装技能和建库分开

建库这件事被拆成两半过：脚本建空骨架，技能填内容。结果是两边都要维护同一套目录约定，用户还得手工贴一段指针进 `AGENTS.md`。这是职责重叠，不是分工。

现在的边界是硬切：

- `install.sh` **只复制技能**，不建目录、不写路由、不碰任何项目文件
- `project-memory` 是**唯一**的建库负责人：`references/init.md` 讲流程、参数、验收和拒绝条件，`scripts/init.sh` 是唯一实现
- 脚本跟着技能一起部署，所以技能调用它、用户直接跑它，走的是同一份代码——**一份实现，两条入口**
- `templates/AGENTS.md.pointer.md` 删掉——技能靠 `AGENTS.local.md` 就能定位，不需要往项目 `AGENTS.md` 里塞文字

为什么不把脚本做成「独立安装器」（让 `install.sh --workspace` 一把建库）：那要求用户机器上有 Skein 源码仓。用 skills-manager 部署技能的人没有那个仓，脚本就找不到。放进技能目录，才有「同一份实现」可言。

这样做的代价是：必须有一个能跑 shell 的 agent 或终端在场。换来的是没有第二份约定、没有手工步骤、也没有"脚本建了一半、技能以为是空的"这种状态。

### 4.8 工作区地图：自动生成，但不算体积

一个工作区里有几十个目录，新 agent 需要先知道「有什么、哪些还活着」，否则只能逐个试探。所以建库时顺手写一张 `kb/facts/workspace-map.md`。

两个具体决定来自实测：

**不算递归体积。** `du -sh` 一个 40 MB 的目录在这台机器上要 21.7 秒，五个就是一百多秒，建库会从几秒变成两分钟。改成「顶层条目数」——毫秒级，同样能看出哪些目录异常臃肿。要真实体积时手工量一次就够。

**备注先取 `package.json` 的 `name@version`，再取 README 首行。** 五个 40 MB 的目录看起来一模一样，只有版本号能区分它们；README 往往还是同一个文件复制过来的。反过来先取 README，这五个就完全分不出来。

地图是快照不是事实：文件头写生成时间，agent 动手前仍要核对目标目录和 `git rev-parse HEAD`。文件由脚本生成、禁止手工编辑，人工说明另写 `facts/workspace-notes.md`——这样刷新地图不会覆盖人的判断。

### 4.9 项目档案：接手一个项目，和接手一个任务是两件事

这是设计里最后补上的一块，起因是一个很具体的质疑：**「在已有项目上建了 Skein 库，另一个 agent 怎么接手干活？难道要原来的 agent 先 handoff 一次？」**

答案是不需要 A，但需要一次**建档**。

**两层分离**：

| 层 | 回答什么 | 存在哪 | 谁维护 |
|---|---|---|---|
| 项目档案 | 这个仓是干什么的、从哪进、怎么跑、细节在哪 | `facts/projects/<仓>.md` | `project-memory` |
| 任务检查点 | 这个任务做到哪、下一步做什么、现场什么状态 | `checkpoints/<task_id>.md` | `task-checkpoint` |

检查点假设「任务已经存在」。已有项目刚建库时没有任务，所以只有检查点接不住——这是缺口，不是用法问题。

**为什么不能要求 A 先 handoff**：A 可能不在场、可能从没做过这个项目、也可能根本没有这个任务。把「理解项目」绑在「某个人在场」上，就回到了 1-2-1 交接，而用户明确说那不是日常场景。

**为什么脚本写不了档案**：`init.sh` 只能读文件系统和 Git 元数据。它能数出「有 8 个仓、最后提交是哪天」，读不出「这个仓解决什么问题」。硬让脚本猜，结果就是一份看起来完整、实则全是推测的文档——比没有更糟，因为下一个人会信。

**为什么不是第 5 个技能**：建档是「项目级慢变事实」的一种，和建库、检索、写回是同一件事的三面。拆出去会让「接管一个项目」变成要在两个技能之间跳。

**先定目标仓，再谈分档**：

```
目标仓（用户指定 / 当前任务涉及）
  → 直接完整建档，不看提交时间
其他仓
  → 保持 TODO，用到再建
```

活跃度三条判据只在「用户没说目标、要批量预建档」时用来排先后：

```
当前任务涉及该仓  /  工作树有未提交改动  /  任一本地分支 90 天内有提交
```

**为什么不能拿它决定「建不建」**：两个 provider 独立审阅都指出同一件事——90 天只能证明本地分支指向了较新的提交，推断不出「用户下一步要接手哪个仓」。两年没动、工作树干净的仓，恰恰最需要档案。把判据降级成「排先后」，这个矛盾就消失了。

**`PARTIAL` 不是「不活跃仓的占位」。** 它表示「开始建了，但 `READY` 准入条件没满足」，缺口必须写清。没被选中的仓保持 `TODO`——一份没有入口和命令的档案比 `TODO` 更糟，因为它看起来建过了。

**`READY` 五条准入**：定位有依据、有可信入口、有运行方法（或明确不适用）、指针指向真实文件、关键缺口已清。字段填满不算数；预算耗尽、只读声明、入口没找到，都是 `PARTIAL`。命令实测不是前提，但每条必须标「未实测」。

**档案是导航，不是事实。** 4 KB / 70 行上限，每句话标来源（源码 / 文档 / 推断），冲突时以 Git 现场为准。

**刷新看内容哈希，不看 HEAD。** 建档时工作树 dirty（内容 B），之后撤销回 HEAD（内容 A），`git diff BASE HEAD` 和 `git status` 都返回空，但档案写的是 B，已经错了。所以头部记 `巡检：路径#哈希前8位`，刷新时逐个 `git hash-object` 重算。只有「档案依据的那份内容没变」才不刷新。

**代价**：建库从几秒变成几分钟，一个目标仓约 5k tokens。这是首次成本，换来此后任何 agent 冷启动只读一份 2 KB 文件就能定位。批量预建档才按仓数线性增长，不做全量。

**只跑脚本的人拿不到档案。** 这是有意的：`init.sh` 会把 `projects/INDEX.md` 的每一项标成 `TODO`，让「库已建、档案未建」这个状态可见，而不是假装建完了。

### 4.10 收尾由什么触发：不是上下文百分比

原设计写「上下文到 60–75% 时写检查点」，但模型看不到这个百分比，宿主也未必给警告。实际结果是检查点几乎不写——五个工作区 0 份，用户只能在换会话时手动要 handoff。

改成**可观察的触发**：

- 阶段结果落地、决策推翻旧做法、遇阻
- 用户说「先到这 / 新开会话 / 明天继续 / 换会话」
- 宿主给出压缩警告

并强制一个可见输出：长任务回复末尾写 `检查点：<路径>` 或 `检查点：无（原因）`。这比在规则里只写「要写」更难忽略。

**同一个 agent 新开会话不写 handoff。** 检查点就是给下一轮的自己看的；handoff 只给另一个 agent 或另一台机器。用户说「写 handoff」但实际还是自己接着干时，写检查点并在回复里说明、给出路径；只有用户坚持要一份文件时才写 handoff。

**规则放在 b 层，不放在 a 层。** 检查点依赖 `AGENTS.local.md` 的 `checkpoints` 键，只有建了 Skein 库的工作区才有；写进全局会让没有库的项目照着做，然后报 `[HANDOFF_GAP]`。`init.sh` 建库时把 `<!-- skein-rules -->` 块写进 `<工作区>/AGENTS.md`（可重复执行，不会重复追加）。全局 §6 只留一句「按项目定义的机制落盘」。

顺带修了一个分发缺口：`~/.codebuddy/CODEBUDDY.md` 原先不在同步目标里，CodeBuddy/WorkBuddy 的用户级记忆收不到 a 层。现在已加入。

## 5. 被否掉的方案

| 方案 | 为什么不选 |
|---|---|
| 继续用单一交接库（一个大 skill 管全部） | 每次开工全量加载，低频规则常驻，等于天天付租金 |
| 拆成 5–6 个技能（读写分离、检索独立等） | 边界变模糊，"先调哪个"变成每次都要做的判断 |
| 自建任务编排服务 | 需要服务器、需要维护，且把私有数据搬到了服务上 |
| 常开向量检索 | 小库上是净负担；阈值不到就不该开 |
| 知识库放代码仓里 | 代码仓可能公开，等于把私有资料一起推出去 |
| 云同步 / 私有远程备份 | 硬需求是"数据不上传"，宁可手动备份 |
| 用 LLM 自动合并知识库冲突 | 冲突的判定需要语义理解，自动合并的错误是静默的，比冲突更贵 |

## 6. 术语表

| 词 | 意思 |
|---|---|
| `AGENTS.local.md` | 工作区根的本机路由文件，五个键，永不提交 |
| `[HANDOFF_GAP]` | "信息不足，我停下"的统一信号，不是错误码 |
| 租约 / lease | 任务认领后的独占期，300 秒，可心跳续 |
| `checkpoint_rev` | 检查点版本号，写入自检用 |
| `repo` | 检查点字段：这次任务落在哪个 git 仓；不在仓里写 `none` |
| `.skein-scope` | 数据目录的归属标记，内容是这个工作区的绝对路径 |
| worktree | Git 的并行工作目录，同一个仓、不同目录、不同分支 |
| `proposals/` | 非写者对知识库的改动建议，由写者合并 |
| 快照 vs 流水 | 快照 = 覆盖成最新；流水 = 只追加不改 |

## 7. 兼容与版本

- 检查点格式带 `schema_version: 1`，格式变更时升版本号
- 技能之间只通过三样东西耦合：`AGENTS.local.md` 的键、检查点的 YAML 头、任务库的 ID
- 换掉任务库（Beads）会让 `agent-handoff` 的强制转派与 `agent-collab` 的认领失效；没有 Beads 时仍能顺序接手（确认旧写者已停），但没有租约、没有转派、也没有并发互斥。换掉 QMD 只影响检索第 4–6 级，前三级照常
