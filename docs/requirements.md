# Skein 需求规格说明书（v2.2）

> 本文档仅定义目标、场景、约束与验收标准，不包含任何具体技术实现或第三方工具选型建议。

## 1. 背景与总目标

解决多 AI 助手在同一工作区长期协作时的上下文断裂、跨助手接手成本高、双助手并发冲突及日常 token 消耗过高的问题。系统需支持单机本地离线运行，在不拖慢日常本职工作的前提下，实现无缝接力、冷启动上手、按需知识检索与安全并发协作。

## 2. 四大核心场景（缺一不可）

### 2.1 乒乓交接（A → B → A）
- 助手 A 完成任务的一部分后停止，助手 B 接手继续推进，随后助手 A 再次返场继续。
- 返场方严禁仅凭旧会话记忆继续操作，必须基于最新现场与状态记录核对后再执行。

### 2.2 双助手同项目协作（两种形态均需支持）
- **形态一：独立子任务并行**：两个助手同时处理同一项目的不同模块或子任务，各自隔离工作现场，互不覆盖改动，完成后统一合入。
- **形态二：同任务实时配合**：两个助手围绕同一未提交现场实时协同（例如一方负责修改，另一方负责审查、测试或查证），通过明确的写权限划分避免冲突。

### 2.3 冷启动接手
- 从未接触过目标项目的全新助手进入工作区后，无需通读全量代码或文档，即可快速获取项目定位、关键入口、运行验证方式与硬性约束并直接上手工作。

### 2.4 大知识库按需调用
- 针对大型复杂项目，将长期有效的事实、架构决策、操作手册及相关知识体系集中整理。
- 严禁全量加载知识库进入上下文；必须按需仅抽出当前任务所需片段，严格控制上下文与 token 消耗。
- 当前范围以**单项目/单工作区知识库**为主，但结构上须为未来扩展**跨项目个人知识体系**预留空间。

## 3. 零准备接手、可验收恢复与中断边界

### 3.1 零准备承诺
- **转出方（A）零准备**：在已建仓的工作区中，A 干到一半停止、中断或切换，不需要 A 提前执行任何交棒整理操作。
- **接手方（B）极简触发**：
  - 当当前子项目仅存在 1 个匹配的未完任务时，用户在 B（或 A 的新会话）只需发出一句简短指令（如“接手”）即可直接恢复，无需先手动切换技能开关或重开会话。
  - 当存在多个匹配的未完任务时，B 必须先列出候选项请用户选择，不得自行猜测。

### 3.2 接手可验收标准
B 接手后必须能准确找回以下 6 项内容，作为“真正接上”的验收依据：
1. 用户最后确认的目标
2. 变更过的约束条件
3. 关键决定及其理由
4. 已经排除的方案（避免重复试错）
5. 当前待验证的假设
6. 可直接执行的下一步

*允许边界*：允许 B 重新查证中断前尚未形成结论的一小段探索过程，不要求全量回放无关历史对话。

### 3.3 写前留痕与中断/后台操作规则
- **写前最小记录**：一次可完成、易于重做且没有待交接决定的小改动，可直接处理，零次 Skein 专用调用。其余可能留下半成品的任务，在第一次实质修改文件或启动长耗时操作之前，必须先留存最小状态记录。
- **窗口状态与写权判定**：A 的客户端窗口仍开着但已停止写入时，B 可以直接接手，不要求先关闭 A 的窗口。
- **后台残留命令冲突判定**：若检测到仍有后台命令正在写入同一工作现场，B 必须先核查进程状态与已有产物，必要时询问用户“等待完成还是终止”，严禁盲目覆盖写入。该场景属于单任务中断冲突，须与“双助手有意实时配合”严格区分。

### 3.4 首次建档覆盖面与按需读取
- 首次建仓时，所有经用户确认纳入范围的子项目都必须具备最小项目档案。
- 接手或日常工作时，**只读取当前涉及子项目的那一份档案**，严禁批量加载整个工作区的其他子项目档案。

### 3.5 长期单助手运行场景
- 跨助手乒乓交接不是日常常态；大量任务会在单一助手中长期连续运行。
- 系统必须支持单助手长期运行时的持续进度留痕（做到哪、下一步、不要重复什么），防止会话压缩、换天或意外中断导致返工。

### 3.6 统一版本管理底座
- 代码、脚本及文档/调研类任务均纳入 Git 仓库管理（非 Git 文档目录在建仓时初始化为 Git 仓库），以 Git 作为现场状态核对、变更追踪与并发隔离的统一基础。

## 4. 技能（Skill）职责分工与开关要求

系统须按职责拆分为互不重叠的 5 类技能，并通过现有的 `skills-manager`（`https://github.com/xingkongliang/skills-manager`）按需管理开关：

| 职责类别 | 核心职责边界 | 启用策略 |
|---|---|---|
| **初次建库技能** | 工作区初始化、建立目录结构与纳入范围子项目的最小档案 | 仅首次建库或新增子项目时启用，建完即卸载 |
| **日常记录技能** | 单助手长期运行时的进度留痕、写前最小记录与避坑记录 | 日常全局常驻 |
| **跨助手接手技能** | 换助手接手、返场核对与冷启动恢复 | 项目级常驻可发现（未触发仅占极少元数据，触发时再读正文） |
| **大知识库技能** | 大型复杂项目的知识库按需抽页、沉淀与整理 | 仅大型/复杂项目按需启用，小型项目不挂载 |
| **并行协作技能** | 双助手同时协作（独立子任务并行或同任务实时配合）时的隔离、协同与收尾 | 仅协作期临时启用，结束即卸载 |

- **开关主体**：默认由人工通过 `skills-manager` 手动开关，助手仅负责在合适时机提醒挂载或卸载。

## 5. 效率、资源与运行约束

1. **日常效率与工具代劳原则**：凡是能由外部工具自动完成的机械采集、状态核对、留痕与锁管理，一律尽量交由外部工具承担，减少助手在完成本职工作之外的时间与 token 消耗。
2. **统一省上下文与省 Token**：低频规则绝不常驻上下文，知识与档案坚持按需最小读取。
3. **优先成熟现成工具**：各功能有现成成熟工具即优先复用，降低自研与维护成本；但工具不可过重（无超大型企业级项目需求），尽量避免不完善的小众工具（除非其精炼完善、缺陷极少）。
4. **日常轻量与资源开销边界**：首次部署复杂或安装包体积略大可以接受；允许本机运行后台服务，内存与磁盘适度占用可接受，但**日常 CPU 占用必须保持低水平**。
5. **单机本地离线**：每个项目单机闭环运行，无跨设备同步需求；数据不上传云端，优先纯本地离线（私人仓库勉强可接受，但以离线为首选）。
6. **不保留历史包袱**：不要求兼容或延续原有 `handoff-kb`，允许完全放弃。
