# 项目档案：契约

`kb/facts/projects/<仓名>.md`，**给要接手的那个仓一份**；其余仓留在索引里标 `TODO`，用到再建。给第一次进这个仓的 agent 看。

不是 README 的副本，也不是源码摘要。它只回答四个问题：这是什么、从哪进、怎么跑、细节在哪。

## 上限

- **硬上限：4 KB / 70 行**，超过就是失败，不截断——重写或拆到 `facts/` 其他文件
- **正常目标：1–2 KB / 30–45 行**。写满上限说明写多了

## 三态

| 状态 | 含义 | 谁来判 |
|---|---|---|
| `TODO` | 索引里有，档案还没建。**不是缺陷，是「用到再建」的正常状态** | `init.sh` 建索引时全标这个 |
| `PARTIAL` | 建了，但 `READY` 准入条件没满足；缺口必须写在「缺口」节 | 建档 agent 逐条核对 |
| `READY` | 五项准入条件全部成立 | 建档 agent 核对后改 |

**`READY` 不等于「命令已验证」。** 从 `package.json` 读到 `npm test` 只说明声明存在，不等于跑通了。字段里必须区分「声明」和「实测」，否则下一个人会把声明当结论。

### READY 准入条件

五条**全部**成立才能标 `READY`，缺一条就是 `PARTIAL`：

| 条件 | 判法 |
|---|---|
| 定位有可追溯依据 | 「定位」节写了依据，且不是凭空推断 |
| 至少一个可信入口，或明确说明本项目不需要入口 | 入口路径真实存在 |
| 能找到运行/测试/开发方法，或明确说明不适用 | 命令有来源，或写「未发现」并说明查过哪 |
| 关键文档指针全部指向真实文件 | `test -f` 逐个过 |
| 影响接手的关键缺口已解决 | 「缺口」节为空，或只剩不影响开工的小项 |

**字段填满 ≠ `READY`。** 预算耗尽、只读了声明、入口没找到——这些都该是 `PARTIAL` 并写清缺口。

**命令实测不是 `READY` 的前提**，但每条命令必须标「未实测」。

## 建档范围与读取深度

**先定目标仓，再谈深度。** 目标仓由用户指定，或就是当前任务正在动的那个仓。

- **有目标仓** → 直接完整建档，**不看活跃度**。一个两年没提交、工作树干净的仓，恰恰最需要这份档案
- **用户没说、又确实要批量预建档** → 才用下面的判据筛「先建哪些」
- **没被选中** → 保持 `TODO`。**不要写 PARTIAL 占位**——那会让人以为建过，实际没有入口和命令。用到时再建

批量预建档时的筛选判据（任一满足即先建）：

```bash
R="<仓路径>"

# 1) 当前任务涉及该仓 —— 由调用方传入，脚本判不了
# 2) 工作树有未提交改动；Git 失败不能当成干净
if dirty="$(git -C "$R" status --porcelain=v1 --untracked-files=normal 2>/dev/null)"; then
  [ -n "$dirty" ] && echo FULL
else
  echo GIT_CHECK_FAILED
fi

# 3) 任一本地分支在最近 90 天有提交
latest="$(git -C "$R" for-each-ref --sort=-committerdate --count=1 \
  --format='%(committerdate:unix)' refs/heads 2>/dev/null)"
[ -n "$latest" ] && [ "$latest" -ge "$(( $(date +%s) - 90*86400 ))" ] && echo FULL
```

**这套判据只回答「先建哪个」，不回答「要不要建」。** 它读不出用户下一步要接手哪个仓，所以永远不能凌驾于目标仓之上。

Git 检查失败 → 保持 `TODO`，原因写进索引备注列。**没有首次提交（`UNBORN`）不是拒绝建档的理由**：README、源码、配置都在就能建，基线写「尚无提交」。

**为什么不用「最后提交超过 90 天」单判据**：实测一个 33 条目、8 个 git 仓的工作区，8 个仓的最后提交全在 4 天内，90 天阈值一个都筛不掉。而「有没有未提交改动」「有没有活跃分支」至少能在不读代码的前提下区分「停更但有新工作」和「真的没在动」——但它仍然只是启发式，不能用来否决目标仓。

## 模板

```markdown
# <仓名>

- 状态：READY | PARTIAL
- 仓库：<相对工作区根的路径>
- 基线：<完整 HEAD SHA> · <分支> · 工作树 clean|dirty
- 巡检：`README.md#8f3a1c5e` `package.json#2b7e90d1` `AGENTS.md#5d1f02ab`
- 建档：<YYYY-MM-DD HH:MM>

## 定位

<一句话：这个仓解决什么问题、面向什么> — 依据：<README.md / 用户确认 / 推断>

## 入口

- `<相对路径>` — <作用> — 依据：<源码 / 文档 / 推断>

（最多 3 条）

## 运行验证

- `<命令>` — <声明来源>，未实测
- 前置：<运行时版本 / 环境变量名 / 依赖服务；没有就不写这一行>
- 未发现构建或测试入口

（最多 2 条命令 + 1 条前置）

## 文档指针

- `README.md` — <一句摘要>；<什么时候该读>
- `AGENTS.md` — 项目约束；**改代码前必读**

（最多 3 条）

## 缺口

- <缺什么、会影响哪类操作>

（`PARTIAL` 必须写清缺什么。`READY` 只允许留不影响开工的小项）
```

「巡检」里的哈希是 `git hash-object -- <文件> | cut -c1-8`，只列建档时**真正读过**的文件。怎么用见「刷新」。

## 字段来源

| 字段 | 来源 | 可以写不确定吗 |
|---|---|---|
| 仓库、基线、工作树 | `git` 与文件系统 | 不能。拿不到就保持 `TODO` |
| 定位 | README、文档、用户确认 | 可以。写「未核实」，不许编 |
| 入口 | 目录结构 + 有限阅读 | 路径可确认，作用允许「推断」 |
| 运行命令 | `package.json` / `Makefile` / 文档 | 可以。写「未发现」，不许猜 |
| 前置环境 | `.nvmrc` / `.python-version` / `.env.example` / compose / CI | 可以。只写名字，不抄值 |
| 文档指针 | 实际存在的文件 | 不能。指针必须指向真实文件 |
| 缺口 | 建档时发现的空白 | 鼓励写 |

**三类来源要分清**，写的时候用一个词标出来：

- `[源码]` — 直接读到的
- `[文档]` — 文档里写的，未验证
- `[推断]` — 从命名或结构猜的，可能错

不标来源的句子，下一任会当事实用。

## 黑名单

不许进档案：

- 源码片段、整份配置文件、完整目录树（`find` / `tree` 全量输出）
- `git diff` 全文、完整日志、完整错误堆栈
- 历史流水账、已完成的小步修改
- API key、密码、token、客户数据
- 当前任务归属、租约、检查点内容（那是 `task-checkpoint` 的事）
- 未经核实的架构评价

## 写入与中断恢复

顺序不许换：

```
1. 写 <仓名>.md.tmp
2. 校验：必填字段齐、≤ 4 KB / 70 行、READY 五条准入逐条过
3. 原子重命名到 <仓名>.md
4. 更新 facts/projects/INDEX.md 的状态列
5. git -C <kb> add -- facts/projects/<仓名>.md facts/projects/INDEX.md
6. git -C <kb> commit --only -m "kb: 建档 <仓名>" -- \
     facts/projects/<仓名>.md facts/projects/INDEX.md
7. 检查第 6 步退出码；非 0 就把索引状态改回与文件一致的值并报告
```

**不要 `git add -A`**：库里可能还有别人正在写的东西，全量暂存会把它们带进这次提交。**不要省掉 `--only`**：它保证提交范围和上面列的路径完全一致。

**「未发现」是合法内容。** 纯文档仓、无测试脚本的仓，写 `无（未发现测试脚本，查过 package.json / Makefile）` 就算填了，不算缺字段——否则每次恢复都会被降回 `TODO` 重跑。

中断后恢复：**先看实际文件，再看索引**。

- 索引写 `READY` 但文件不存在 / 字段不全 → 降回 `TODO`
- 索引写 `TODO` 但文件完整 → 核对后改成真实状态
- 有 `.tmp` 残留 → 删掉重写，不要续写

## 命名

- 普通仓：`<仓目录名>.md`
- 工作区根自身（索引里相对路径是 `.`）：`<工作区目录名>.md`
- 同名仓：`<仓目录名>-<路径 hash 前 8 位>.md`，hash 输入是**工作区相对路径**，不是 HEAD
- 索引里永远记相对路径，不靠文件名定位

## 刷新

**按需增量，不设定时任务。**

「巡检」就是头部那行列出的文件——建档时**实际读过**的那几个，不是固定三件套。每项写成 `路径#内容哈希前 8 位`：

```bash
git -C "$R" hash-object -- README.md | cut -c1-8
```

刷新时逐个重算，与档案里记的比：

```bash
# 文件不在了，或哈希对不上 → 需要刷新
for item in 'README.md#8f3a1c5e' 'package.json#2b7e90d1'; do
  f="${item%#*}"; want="${item##*#}"
  now="$(git -C "$R" hash-object -- "$f" 2>/dev/null | cut -c1-8)"
  if [ -z "$now" ] || [ "$now" != "$want" ]; then echo "STALE $f"; fi
done
```

**为什么用内容哈希，而不是 `git diff BASE HEAD` + `git status`：**

建档时工作树是 dirty 的（内容 B），之后用户撤销修改回到 HEAD（内容 A）。两条 Git 命令都返回空，但档案写的是 B，已经错了。哈希只看「档案依据的那份内容现在还在不在」，不关心它是提交、暂存还是工作树。

- 哈希一致 → 不刷新
- 哈希不一致或文件不存在 → 刷新受影响字段
- `hash-object` 报错 → 标「待核实」，不能判定为「没变」

**没写巡检行**（老档案）→ 按正文里出现过的路径逐个算哈希，不要只比 `README.md`。

**归档时的 HEAD 和 clean/dirty 是快照，不是当前状态。** 档案头部已经写了「建档」时间；接手方要用现场 `git status` 复核，不能拿档案头当现状。

## 冲突

档案与现场冲突时，**以 Git 现场和实际文件为准**。档案只是导航。

冲突处理顺序：

1. 按真实代码/配置执行，不要为了迁就档案走错路径
2. 把冲突字段改成实际值，或标「待核实」
3. 改完顺手 `git commit`，让下一个人看到的是修过的版本

**不许**用档案否认当前文件的变化，也不许因为源码变了就宣布旧决策失效——那是两回事。
